# Four Local mics from one interface on a Linux Stage

Research for [issue #33](https://github.com/Marcowich0/OpenStar/issues/33) ("Local mic mapping"; map in [issue #1](https://github.com/Marcowich0/OpenStar/issues/1)). Sources read on 2026-11-24. Follows [browser-microphone-limits.md](https://github.com/Marcowich0/OpenStar/blob/research/browser-microphone-limits/docs/research/browser-microphone-limits.md) on branch `research/browser-microphone-limits`.

Setup in question: a Linux PC (PipeWire desktop) running a Chromium browser as the Stage, a Behringer UMC404HD (four mic inputs, USB class compliant) and four Shure SM58s.

Every claim carries a source and a confidence: **high** means read directly in source code or official docs at the revision linked; **medium** means read in source but depends on runtime behaviour or on code paths I did not trace end to end; **low** means inferred or second-hand. **Unverified** means no primary source was found. Nothing here was measured on the hardware.

Revisions read:

## 1. Chromium on Linux

### Which backend runs

Chromium has three Linux audio backends: ALSA, PulseAudio and CRAS (ChromeOS). There is **no PipeWire backend** in `media/audio` ([directory](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/media/audio/)). It tries PulseAudio first and falls back to ALSA only if PulseAudio cannot be initialised ([audio_manager_linux.cc#46](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/media/audio/linux/audio_manager_linux.cc#46)). On a PipeWire desktop it therefore talks to `pipewire-pulse`. **High.**

### The cap, and where it is

There are two independent limits.

1. **The Pulse backend asks for stereo, always.** `AudioManagerPulse::GetInputStreamParameters()` returns `ChannelLayoutConfig::Stereo()` for every input device, whatever the source has ([audio_manager_pulse.cc#126-153](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/media/audio/pulse/audio_manager_pulse.cc#126); same line at stable [#136](https://chromium.googlesource.com/chromium/src/+/refs/tags/158.0.8127.88/media/audio/pulse/audio_manager_pulse.cc#136)). The record stream is then created with that channel count and a FL/FR channel map, and without `PA_STREAM_NO_REMIX_CHANNELS` ([pulse_util.cc#450-505](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/media/audio/pulse/pulse_util.cc#450)), so the sound server mixes the source down to two channels. The ALSA backend also hard-codes stereo ([audio_manager_alsa.cc#87-94](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/media/audio/alsa/audio_manager_alsa.cc#87)). **High.**
2. **A hard limit of 3 input channels on every platform.** `AudioManagerBase::MakeAudioInputStream()` refuses parameters with more than `kMaxInputChannels = 3` channels ([audio_manager_base.cc#49](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/media/audio/audio_manager_base.cc#49), [#506](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/media/audio/audio_manager_base.cc#506); same at stable [#49](https://chromium.googlesource.com/chromium/src/+/refs/tags/158.0.8127.88/media/audio/audio_manager_base.cc#49)). Even a patched Pulse backend could not deliver 4 channels without changing this too. **High.**

**No flag lifts it.** The only Linux input switches in `media_switches.cc` are `--alsa-input-device` (picks the ALSA device, still stereo) and `--use-cras` ([media_switches.cc#298](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/media/base/media_switches.cc#298), [#340](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/media/base/media_switches.cc#340)). `kMaxInputChannels` is a compile-time constant. **High.**

What the downmix does to a 4-channel UMC404HD source when Chromium asks for FL/FR depends on the source's channel positions (PipeWire's channel mixer, [channelmix-ops.c](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/spa/plugins/audioconvert/channelmix-ops.c#L231)). **Medium** (read in source, not measured):

- Source positioned FL FR RL RR (the no-UCM "Multichannel Input"): rear channels are mixed into the front at the surround level ([#394-409](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/spa/plugins/audioconvert/channelmix-ops.c#L394)). Left would carry input 1 plus some of input 3. **Not clean.**
- Source positioned AUX0 to AUX3 ("Pro Audio"): positions are unknown to the mixer, so channels are paired by index ([#231-252](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/spa/plugins/audioconvert/channelmix-ops.c#L231)). Chromium would get inputs 1 and 2; inputs 3 and 4 are dropped.
- A mono source (the UCM "Input N" sources): the one channel is copied to both outputs. Harmless; read channel 0.

### Audio processing

With Chromium's processing (APM) on, the allowed channel counts are 1 and the device's count, i.e. 1 or 2 on Linux; the sample rate is fixed to APM's rate. With processing off, only the device's count (2) and rate are offered ([media_stream_constraints_util_audio.cc#878-888](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/third_party/blink/renderer/modules/mediastream/media_stream_constraints_util_audio.cc#878), [#903](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/third_party/blink/renderer/modules/mediastream/media_stream_constraints_util_audio.cc#903), [#972](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/third_party/blink/renderer/modules/mediastream/media_stream_constraints_util_audio.cc#972), [#997](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/third_party/blink/renderer/modules/mediastream/media_stream_constraints_util_audio.cc#997)). Processing therefore permits mono but does not force it when `channelCount: 2` is requested. **High.** For pitch detection all processing should be off anyway.

### Several devices at once

`AudioManagerBase` allows up to `kMaxInputStreams = 16` open input streams ([audio_manager_base.cc#47](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/media/audio/audio_manager_base.cc#47), [#514](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/media/audio/audio_manager_base.cc#514)), and each `getUserMedia()` with a distinct `deviceId` opens its own Pulse record stream. Nothing found restricts this on Linux. **Medium:** read in code; no first-party test or statement found, so it still needs the hardware test the earlier research asked for.

Device enumeration skips monitor sources and sources whose ports are all marked unavailable ([audio_manager_pulse.cc#397-416](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/media/audio/pulse/audio_manager_pulse.cc#397)). A remapped or loopback source is an ordinary source and is listed. **Medium.**

## 2. Firefox on Linux

- **Backend.** cubeb's Linux order is the Rust PulseAudio backend first, then the C one, then JACK and others; there is no PipeWire backend ([cubeb.c#223-235](https://hg.mozilla.org/mozilla-central/file/82548796f68290045199f300c043fd940f2c3a86/media/libcubeb/src/cubeb.c#l223)). **High.**
- **Device channel count.** cubeb-pulse reports an input device's `max_channels` as the Pulse source's channel-map size ([context.rs#490](https://hg.mozilla.org/mozilla-central/file/82548796f68290045199f300c043fd940f2c3a86/third_party/rust/cubeb-pulse/src/backend/context.rs#l490)). Firefox exposes that as `channelCount.max` and, with no constraint and the default pref `media.getusermedia.audio.max_channels = 0`, uses all of them ([MediaEngineWebRTCAudio.cpp#138-158](https://hg.mozilla.org/mozilla-central/file/82548796f68290045199f300c043fd940f2c3a86/dom/media/webrtc/MediaEngineWebRTCAudio.cpp#l138), [all.js#268](https://hg.mozilla.org/mozilla-central/file/82548796f68290045199f300c043fd940f2c3a86/modules/libpref/init/all.js#l268)). The input stream is opened with an undefined layout, so Pulse's default map for that count is used ([GraphDriver.cpp#619-621](https://hg.mozilla.org/mozilla-central/file/82548796f68290045199f300c043fd940f2c3a86/dom/media/GraphDriver.cpp#l619), [stream.rs#948-966](https://hg.mozilla.org/mozilla-central/file/82548796f68290045199f300c043fd940f2c3a86/third_party/rust/cubeb-pulse/src/backend/stream.rs#l948)). **High.**
- **Processing forces mono above 2 channels.** `MAX_CHANNELS` is 2; when processing is active and the input has more than 2 channels, Firefox sums all channels into one ([MediaEngineWebRTCAudio.cpp#31](https://hg.mozilla.org/mozilla-central/file/82548796f68290045199f300c043fd940f2c3a86/dom/media/webrtc/MediaEngineWebRTCAudio.cpp#l31), [#954-975](https://hg.mozilla.org/mozilla-central/file/82548796f68290045199f300c043fd940f2c3a86/dom/media/webrtc/MediaEngineWebRTCAudio.cpp#l954)). Pass-through (all channels kept) happens only when echo cancellation, gain control and noise suppression are all off ([#545-556](https://hg.mozilla.org/mozilla-central/file/82548796f68290045199f300c043fd940f2c3a86/dom/media/webrtc/MediaEngineWebRTCAudio.cpp#l545)). **High.**
- **`channelCount > 2` honoured?** Yes in the code path above. Mozilla's 2017 post says Firefox defaults to stereo and needs `exact` to demand 4 ([Mozilla WebRTC blog](https://blog.mozilla.org/webrtc/channelcount-microphone-constraint/)); the current code defaults to the device maximum instead. End to end it is **not confirmed**: [bug 2012662](https://bugzilla.mozilla.org/show_bug.cgi?id=2012662) (Ubuntu, Firefox 142, 8-channel capture card) shows `channelCount.max: 8` but only two channels heard; it is UNCONFIRMED and undiagnosed. **Medium.**
- **Several devices at once.** Supported since [bug 1238038](https://bugzilla.mozilla.org/show_bug.cgi?id=1238038) (fixed 2022), with a test that opens every microphone at once ([test_multi_mics.html](https://hg.mozilla.org/mozilla-central/file/82548796f68290045199f300c043fd940f2c3a86/dom/media/webrtc/tests/mochitests/test_multi_mics.html)). **High.**

## 3. WebKitGTK (Tauri's Linux webview)

- Microphones are found with a GStreamer device monitor filtered on `Audio/Source` with caps `audio/x-raw`; the capture pipeline's caps filter only ever sets `rate` ([GStreamerCaptureDeviceManager.cpp#326-333](https://github.com/WebKit/WebKit/blob/29a3b076140c4fb61d8921f7ca1c6c3ed3678c73/Source/WebCore/platform/mediastream/gstreamer/GStreamerCaptureDeviceManager.cpp#L326), [GStreamerAudioCapturer.cpp#45](https://github.com/WebKit/WebKit/blob/29a3b076140c4fb61d8921f7ca1c6c3ed3678c73/Source/WebCore/platform/mediastream/gstreamer/GStreamerAudioCapturer.cpp#L45), [#91-106](https://github.com/WebKit/WebKit/blob/29a3b076140c4fb61d8921f7ca1c6c3ed3678c73/Source/WebCore/platform/mediastream/gstreamer/GStreamerAudioCapturer.cpp#L91)). Whether the device element is `pulsesrc` or `pipewiresrc` depends on which GStreamer device provider ranks higher on the system. **High** for the code; **unverified** which provider wins.
- The supported audio constraints are `deviceId`, `echoCancellation`, `volume` and `sampleRate`; **there is no `channelCount`** ([GStreamerAudioCaptureSource.cpp#173-179](https://github.com/WebKit/WebKit/blob/29a3b076140c4fb61d8921f7ca1c6c3ed3678c73/Source/WebCore/platform/mediastream/gstreamer/GStreamerAudioCaptureSource.cpp#L173)). **High.**
- How many channels reach Web Audio in WebKitGTK: **unverified.**
- WebKit notes there is no audio desktop portal yet ([GStreamerAudioCaptureSource.cpp#50-54](https://github.com/WebKit/WebKit/blob/29a3b076140c4fb61d8921f7ca1c6c3ed3678c73/Source/WebCore/platform/mediastream/gstreamer/GStreamerAudioCaptureSource.cpp#L50)). **High.**
- Tauri's wry forwards WebKitGTK media permission requests to the app's handler ([wry webkitgtk/mod.rs#593-610](https://github.com/tauri-apps/wry/blob/9f398acad6e76b01fdbf95761e3bc3ce3e2e9fc5/src/webkitgtk/mod.rs#L593)). Whether media stream is turned on by default in a Tauri app: **unverified.**

## 4. Electron

Electron embeds Chromium's content layer and its audio service, so the stereo request and the 3-channel limit above apply unchanged. No Electron API or switch for input channel count was found. **Medium** (absence of evidence). What Electron adds is a Node.js main process, which can load a native addon to capture audio; that is option C or D below in another wrapper, not a browser capability.

## 5. PipeWire and the UMC404HD

### How it appears

It depends on whether ALSA UCM is used.

**With UCM (the default on current distros).** alsa-ucm-conf matches the UMC404HD by USB id `1397:0509` ([USB-Audio.conf#262](https://github.com/alsa-project/alsa-ucm-conf/blob/4bbf5ccddddd6aa0b8541b621129bc9bed5819b6/ucm2/USB-Audio/USB-Audio.conf#L262)). Its `HiFi` use case defines two stereo outputs ("Line A", "Line B") and **four mono capture devices, `Mic1` to `Mic4`, commented "Input 1" to "Input 4"**, each taking one hardware channel of the 4-channel PCM through `SplitPCM` ([UMC404HD-HiFi.conf](https://github.com/alsa-project/alsa-ucm-conf/blob/4bbf5ccddddd6aa0b8541b621129bc9bed5819b6/ucm2/USB-Audio/Behringer/UMC404HD-HiFi.conf)). A second use case, `Direct`, exposes the raw 4-in/4-out PCM ([UMC404HD.conf](https://github.com/alsa-project/alsa-ucm-conf/blob/4bbf5ccddddd6aa0b8541b621129bc9bed5819b6/ucm2/USB-Audio/Behringer/UMC404HD.conf)). **High.**

- The profile was added in October 2023 and first shipped in alsa-ucm-conf **1.2.11** (January 2024) ([commit d0c630e0](https://github.com/alsa-project/alsa-ucm-conf/commit/d0c630e042)). Ubuntu 26.04 ships alsa-ucm-conf 1.2.15.3, PipeWire 1.6.2 and WirePlumber 0.5.13 ([Launchpad](https://launchpad.net/ubuntu/resolute/+source/alsa-ucm-conf)). **High.**
- WirePlumber turns on PipeWire-side SplitPCM handling for every ALSA card (`api.alsa.split-enable = true`, [alsa.lua#37-43](https://gitlab.freedesktop.org/pipewire/wireplumber/-/blob/e633312c318468e39e17595876b9631367e75a05/src/scripts/monitors/alsa.lua#L37)). For split devices it opens the hardware once as a hidden `Audio/Source/Internal` node and creates one loopback `Audio/Source` per UCM device, with `stream.dont-remix`, `node.dont-fallback` and `node.linger` set ([alsa.lua#111-200](https://gitlab.freedesktop.org/pipewire/wireplumber/-/blob/e633312c318468e39e17595876b9631367e75a05/src/scripts/monitors/alsa.lua#L111), [#513-560](https://gitlab.freedesktop.org/pipewire/wireplumber/-/blob/e633312c318468e39e17595876b9631367e75a05/src/scripts/monitors/alsa.lua#L513); key documented in [keys.h#48](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/spa/include/spa/utils/keys.h#L48)). This landed in WirePlumber in December 2024 ([commit 4d02d027](https://gitlab.freedesktop.org/pipewire/wireplumber/-/commit/4d02d027)). **High.**
- So under the `HiFi` profile the Stage should see **four mono sources** that Chromium can open as four devices. **Unverified on hardware**, including the exact node names (expected pattern `alsa_input.usb-BEHRINGER_UMC404HD_192k-00.HiFi__Mic1__source`, from the naming code in [alsa.lua#423-436](https://gitlab.freedesktop.org/pipewire/wireplumber/-/blob/e633312c318468e39e17595876b9631367e75a05/src/scripts/monitors/alsa.lua#L423); **low**) and whether WirePlumber picks `HiFi`, `Direct` or `Pro Audio` on first plug (**unverified**). WirePlumber remembers the chosen profile per device by default (`device.restore-profile = true`, [wireplumber.conf#1005-1010](https://gitlab.freedesktop.org/pipewire/wireplumber/-/blob/e633312c318468e39e17595876b9631367e75a05/src/config/wireplumber.conf#L1005)). **High.**
- Older reports of UMC-series regressions exist ([PipeWire #2703](https://gitlab.freedesktop.org/pipewire/pipewire/-/issues/2703), 2022, closed). **Low** relevance to current versions.

**Without UCM** (older distros, or `api.alsa.use-ucm = false`). PipeWire's default profile set offers a fallback `multichannel-input` mapping on `hw:` with channel map `left,right,rear-left,rear-right` ([default.conf#568-574](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/spa/plugins/alsa/mixer/profile-sets/default.conf#L568)), or an "Analog Surround 4.0" mapping with the same positions ([#144-149](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/spa/plugins/alsa/mixer/profile-sets/default.conf#L144)). Which one the UMC404HD gets is **unverified**.

**Pro Audio.** ACP always adds a `pro-audio` profile ([acp.c#378](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/spa/plugins/alsa/acp/acp.c#L378)). The PipeWire wiki's UMC404HD example names the capture node `alsa_input.usb-BEHRINGER_UMC404HD_192k-00.pro-input-0` with positions `AUX0`..`AUX3` ([wiki: Virtual Devices, "Behringer UMC404HD Microphone/Guitar Virtual Sources"](https://gitlab.freedesktop.org/pipewire/pipewire/-/wikis/Virtual-Devices#behringer-umc404hd-microphoneguitar-virtual-sources)). **High** (official wiki).

### Splitting it yourself

Needed only if the UCM sources are not available or not wanted.

- **PulseAudio-style, at runtime:** `pactl load-module module-remap-source master=<node> channels=1 master_channel_map=aux0 channel_map=mono remix=no source_name=...`, once per input. pipewire-pulse implements it by loading `libpipewire-module-loopback` inside the pipewire-pulse process ([pulse-module-remap-source.c#100](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/src/modules/module-protocol-pulse/modules/pulse-module-remap-source.c#L100)). **High.**
- **Native, at runtime:** `pw-loopback`, which runs the loopback in its own process, so it lasts only while that process runs. **Medium** (tool behaviour from the module docs, not traced).
- **Native, persistent:** a `context.modules` entry for `libpipewire-module-loopback` in `~/.config/pipewire/pipewire.conf.d/`, as in the wiki example above; the module's own docs show the same pattern with `target.object` and `stream.dont-remix` ([module-loopback.c#85-135](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/src/modules/module-loopback.c#L85)). Or `pulse.cmd` entries in `~/.config/pipewire/pipewire-pulse.conf.d/` ([pipewire-pulse.conf.in#77-92](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/src/daemon/pipewire-pulse.conf.in#L77), [pipewire-pulse.conf(5)](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/doc/dox/config/pipewire-pulse.conf.5.md)). **High.**
- **WirePlumber:** a Lua script or rule can create such loopbacks when the device appears; WirePlumber's own SplitPCM code is a worked example ([alsa.lua#150-200](https://gitlab.freedesktop.org/pipewire/wireplumber/-/blob/e633312c318468e39e17595876b9631367e75a05/src/scripts/monitors/alsa.lua#L150)). **Medium.**

### Who may do it

- **Unprivileged app, no sandbox:** yes. pipewire-pulse allows module loading for every client unless `pulse.allow-module-loading = false`, which defaults to true; `LOAD_MODULE` performs no per-client access check ([pulse-server.c#60](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/src/modules/module-protocol-pulse/pulse-server.c#L60), [#5104-5150](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/src/modules/module-protocol-pulse/pulse-server.c#L5104), [#5580](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/src/modules/module-protocol-pulse/pulse-server.c#L5580)). Non-sandboxed native PipeWire clients get full permissions ([module-access.c#220-250](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/src/modules/module-access.c#L220)). **High.**
- **Flatpak with `--socket=pulseaudio`:** pipewire-pulse marks the client `access=flatpak` and gives it the "Manager" category only if the app has `--device=all` ([server.c#453-485](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/src/modules/module-protocol-pulse/server.c#L453)). WirePlumber then gives a plain Flatpak client read and execute permissions (RX) on all objects, and full permissions with "Manager" ([find-flatpak-access.lua#14-18](https://gitlab.freedesktop.org/pipewire/wireplumber/-/blob/e633312c318468e39e17595876b9631367e75a05/src/scripts/client/find-flatpak-access.lua#L14)). But module loading is not gated on that access, and the loaded module runs in pipewire-pulse's own unrestricted context ([pulse-module-remap-source.c#100](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/src/modules/module-protocol-pulse/modules/pulse-module-remap-source.c#L100)). So **a Flatpak with only the PulseAudio socket can create the split at runtime.** **Medium-high** (source read; not tested).
- **Flatpak with the native PipeWire socket** (`--filesystem=xdg-run/pipewire-0`, community practice, not in Flatpak's docs): the client is detected as Flatpak ([module-access.c#201](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/src/modules/module-access.c#L201)) and gets RX unless it has `--device=all`. Whether an RX client can publish a loopback source that other apps can open: **unverified.**
- Flatpak's docs state `--socket=pulseaudio` includes mic input and ALSA devices in `/dev/snd` ([Flatpak: Sandbox permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html)). No socket or portal for PipeWire audio is documented there. **High.**

### Persistence

- Runtime-loaded pulse modules live in pipewire-pulse and are gone when it restarts (logout, reboot, crash). **Medium.**
- Config fragments are re-read on every start. **High** (docs above).
- On replug, a loopback whose `target.object` names the device node relinks when that node returns; `node.dont-fallback = true` stops it from falling back to another mic meanwhile, and `node.linger` keeps the virtual source present. WirePlumber's own split loopbacks use exactly these properties ([alsa.lua#176-186](https://gitlab.freedesktop.org/pipewire/wireplumber/-/blob/e633312c318468e39e17595876b9631367e75a05/src/scripts/monitors/alsa.lua#L176)). **Medium**; not tested.
- A Flatpak cannot write `~/.config/pipewire` without a filesystem permission for it, because its config home is remapped. **Low** (general Flatpak behaviour; not re-read for this note).

## 6. Native capture from Rust

- **cpal 0.18** (0.18.2, 2026-08-16) has ALSA always, plus opt-in Cargo features `pipewire` (native PipeWire API, via the `pipewire` crate 0.10) and `pulseaudio` (pure-Rust protocol client), both new in 0.18.0, and `jack` ([Cargo.toml](https://github.com/RustAudio/cpal/blob/v0.18.2/Cargo.toml), [CHANGELOG](https://github.com/RustAudio/cpal/blob/44ba7ad0c413d10de12f179091423a569a73395c/CHANGELOG.md)). The PipeWire host reads a node's `audio.channels`; the PulseAudio host builds configs from the source's own sample spec and channel map and supports any channel count, using FL FR RL RR for 4 channels ([pulseaudio/mod.rs#536-560](https://github.com/RustAudio/cpal/blob/v0.18.2/src/host/pulseaudio/mod.rs#L536)). Capturing all 4 channels of the device node is therefore supported by the API. **High** (code); **unverified** in practice. The ALSA host would need exclusive access to `hw:` and fights PipeWire for it. **Medium.**
- **pipewire-rs** (`pipewire` 0.10.1): its `audio-capture` example connects a capture stream with no fixed channel count, so it receives the node's native channels, and prints a meter per channel ([audio-capture.rs](https://gitlab.freedesktop.org/pipewire/pipewire-rs/-/blob/8f8e22120d9e8d80dbd326602747f8f8d20796bc/pipewire/examples/audio-capture.rs)). **High.**
- **Flatpak:** with `--socket=pulseaudio`, a native app can record through pipewire-pulse (cpal's `pulseaudio` host) as a Flatpak-access client; there is no microphone portal to ask ([Flatpak docs](https://docs.flatpak.org/en/latest/sandbox-permissions.html), [WebKit comment](https://github.com/WebKit/WebKit/blob/29a3b076140c4fb61d8921f7ca1c6c3ed3678c73/Source/WebCore/platform/mediastream/gstreamer/GStreamerAudioCaptureSource.cpp#L50)). Native PipeWire needs the `xdg-run/pipewire-0` filesystem permission, which GNOME Software flags as unsafe ([gnome-software #2329](https://gitlab.gnome.org/GNOME/gnome-software/-/issues/2329)). **Medium.**

## 7. Stable device identity

- **PipeWire.** WirePlumber names a card `alsa_card.<device.name or device.bus-id or device.bus-path>` ([alsa.lua#625-633](https://gitlab.freedesktop.org/pipewire/wireplumber/-/blob/e633312c318468e39e17595876b9631367e75a05/src/scripts/monitors/alsa.lua#L625)); `device.bus-id` is udev's `ID_ID` ([alsa-udev.c#638-649](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/92025ca59716a8dd20a3866a0b89dc6a538a3e41/spa/plugins/alsa/alsa-udev.c#L638)), which systemd builds as `ID_BUS-ID_SERIAL-ID_USB_INTERFACE_NUM` ([78-sound-card.rules#62-65](https://github.com/systemd/systemd/blob/main/rules.d/78-sound-card.rules#L62)). Node names are the card name plus the profile mapping. So the name does not depend on the USB port or plug order. **High.** The wiki's node name `usb-BEHRINGER_UMC404HD_192k-00` contains no unit serial, so two identical interfaces would collide and the second gets a `.2` suffix ([alsa.lua#635-642](https://gitlab.freedesktop.org/pipewire/wireplumber/-/blob/e633312c318468e39e17595876b9631367e75a05/src/scripts/monitors/alsa.lua#L635)). **Medium.** `device.bus-path` (`ID_PATH`, port-dependent) and `device.serial` are also published as properties. **High.**
- **ALSA card id/index.** The index depends on probe order; the id string is not unique across identical cards. **Low** (general ALSA knowledge; not re-read).
- **Chromium `deviceId`.** The raw id of a Pulse input is the source name, i.e. the PipeWire `node.name` ([audio_manager_pulse.cc#416](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/media/audio/pulse/audio_manager_pulse.cc#416)). The page sees `HMAC-SHA256(key = serialised origin, data = raw id + per-site salt)` as lower-case hex ([media_devices_util.cc#239-258](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/content/browser/media/media_devices_util.cc#239)). The salt comes from a per-storage-key salt service and is deleted with that site's data ([media_device_salt_service.h](https://chromium.googlesource.com/chromium/src/+/aa6986cdff38f2d796b8dde01ec5a16b43235a86/components/media_device_salt/media_device_salt_service.h)). So the `deviceId` survives a replug and a reboot as long as the node name and the site data stay; it changes per origin and when site data is cleared. **High** for the derivation, **medium** for "survives replug" (not tested). `label` (the source description) is a usable fallback key.

## 8. Prior art

- **AllKaraoke** (browser): every input is a `(deviceId, channel)` pair. It opens each device, reads `getSettings().channelCount` and offers one input per channel, so a stereo SingStar dongle becomes two mics; channels are separated with a `ChannelSplitter` ([microphone.ts#68-90](https://github.com/Asvarox/allkaraoke/blob/213a42b529b92d46ad49e65e785d1d6eba39121b/src/routes/select-input/input-sources/microphone.ts#L68), [mic-input.tsx#40-50](https://github.com/Asvarox/allkaraoke/blob/213a42b529b92d46ad49e65e785d1d6eba39121b/src/modules/game-engine/input/mic-input.tsx#L40)). It inherits the browser's 2-channel limit.
- **UltraStar Play** (Unity): a mic profile is a device plus a `ChannelIndex` ([MicProfile.cs#12](https://github.com/UltraStar-Deluxe/Play/blob/a4aaa0b31327062a92d12b5e4cab4d80777f2a3f/UltraStar%20Play/Packages/playshared/Runtime/Microphone/MicProfile.cs#L12)). Its Companion App does pitch detection on the phone and sends **pitch events per beat**, not audio, to the main game ([ClientSideMicDataSender.cs#91-148](https://github.com/UltraStar-Deluxe/Play/blob/a4aaa0b31327062a92d12b5e4cab4d80777f2a3f/UltraStar%20Play%20Companion/Assets/Common/Network/ClientSideMicDataSender.cs#L91)). That is the same shape as option C.
- **Performous** (native, PortAudio): a device spec maps channels to mic colours, e.g. `dev="USBMIC" mics="blue,red"` ([schema.xml#370-372](https://github.com/performous/performous/blob/80f8e3c30b08df5395e24d41442d8144aa718121/data/config/schema.xml#L370), [main.cc#353](https://github.com/performous/performous/blob/80f8e3c30b08df5395e24d41442d8144aa718121/game/main.cc#L353)).
- **Vocaluxe** (native): each player's mic config is device, driver and channel ([CRecord.cs#135-151](https://github.com/Vocaluxe/Vocaluxe/blob/dfc721c9137cd0b3cbd4d69285e7930a2290f453/Vocaluxe/Base/CRecord.cs#L135)).

The native games all treat "one channel of one device" as the unit of a mic; the browser game is capped at two channels per device.

## Facts that decide between the options

Options: **(A)** a browser reads all 4 channels of one device; **(B)** browser plus a PipeWire split, created automatically; **(C)** a native Rust mic bridge that sends Pitch readings like a Phone; **(D)** a native Stage shell.

1. **(A) is impossible in Chromium.** Pulse input is always opened as stereo, and every input stream with more than 3 channels is rejected in `AudioManagerBase`; no flag changes either (§1). Firefox could do it in principle, with all processing off, but end-to-end 4-channel capture is unconfirmed (§2), and Chromium is the Stage.
2. **The UMC404HD may already be split for us.** alsa-ucm-conf 1.2.11+ plus WirePlumber's SplitPCM support (present in Ubuntu 26.04) should expose four mono sources "Input 1" to "Input 4" under the `HiFi` profile (§5). If that holds on the owner's Stage, (B) needs no split of our own: only "make sure the `HiFi` profile is active" plus four `getUserMedia()` calls. This is the single most valuable thing to test.
3. **If a split is needed, it is cheap and allowed.** Any client of pipewire-pulse, even a Flatpak with only `--socket=pulseaudio`, can load `module-remap-source` at runtime with no access check; a config fragment makes it permanent (§5). The catch: runtime splits vanish when pipewire-pulse restarts, so something must recreate them, and channel positions decide whether the result is clean.
4. **Chromium should hold four devices at once** (16-stream limit, no Linux restriction found), and their `deviceId`s should be stable across replug because they hash the PipeWire node name (§1, §7). Both are read from code, not tested.
5. **(C) is well supported if needed.** cpal 0.18's PulseAudio host or pipewire-rs capture all 4 channels from one node, and a Flatpak needs only `--socket=pulseaudio`. UltraStar Play's Companion App already uses the "send pitch, not audio" design (§6, §8). (D) adds nothing for capture that (C) lacks.

## Left for a test on the Stage hardware

2. In Chromium: `enumerateDevices()` lists them; four `getUserMedia({audio: {deviceId: {exact}, echoCancellation: false, noiseSuppression: false, autoGainControl: false}})` calls run at once; each track carries only its own input.
3. Unplug and replug: do the four `deviceId`s stay the same and do open tracks end cleanly?
4. If `HiFi` is missing: `module-remap-source` from `pactl`, from a Flatpak, and after a pipewire-pulse restart.
5. If (C) is pursued: cpal `pulseaudio` host opening the 4-channel node from inside a Flatpak.
